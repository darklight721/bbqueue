# One Session host per Active session

An Active session of a Shared club is changed by only one device: the Session host, the Organizer who started it or later took it over. The host keeps running the Session fully offline exactly as before and uploads its latest copy of the Session when online; everyone else sees it live, read-only. Players ask for their own Sitting out or leaving through separate requests that the host applies in order, skipping any that no longer make sense. We chose this over letting any Organizer change the Session, because the queueing engine uses randomness and offline changes from two devices would conflict (two Matches started on one Court) with no sensible merge.

## Consequences

- Another Organizer can take over at once; changes the old host made offline and never uploaded are lost, and the old host's device becomes read-only.
- A Player's request waits ("Waiting for host") while the host is offline.
- Moving to "any Organizer can change it" later means replaying named operations on the server with a seeded random source per operation.
- Each Shared club has one fixed record for its Active session (`clubs/{clubId}/activeSession/current`), so "at most one per Club" is part of the layout. It holds the whole Session as JSON text (Firestore has no arrays inside arrays), the Session's id (fixed when it starts), the host's uid, Account ID and name, and the server's time of the last upload. Security Rules let an Organizer create it only when none exists, only the host update or delete it, and anyone on the Club read it. Updates are the most frequent writes, so the rules decide from the record alone: a host who loses the Organizer Role keeps uploading until somebody takes over.
- The host's device saves every change on the device first. A coalescing uploader then sends the latest whole copy about a second after the last change, one write at a time and only while online; coming back online sends the latest copy once, instead of replaying a backlog of copies from Firestore's offline queue.
- A Player's request is a record under the Active session (`…/activeSession/current/requests/{id}`), so it belongs to the Session, not to the host. The host's device applies pending requests in the order they were made through the engine, checks the requester owns the Session player (the Account copied onto it at Start, which the rules can't see), and marks a request `applied` only after an uploaded copy of the Session that holds its id has reached the server: the Session keeps the ids of the requests applied to it (`appliedRequestIds`), so a request is applied once, across reloads and take overs, and a plain change that was still uploading when the request was applied doesn't count. A new host therefore finds whatever the old host hadn't got through.
