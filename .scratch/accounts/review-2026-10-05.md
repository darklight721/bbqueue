## Must fix before push

### Security

- ✅ **S1. Bad Session data from the server can crash every member's app, and the crash persists.** `toActiveSession` / `toEndedSession` (firebaseSessions.ts:761-787, :715-734) only check the top-level shape, and the data is stored as it arrives (storage.ts:170-186, store.ts:59-65). For example, one host upload containing `matches:[null]` makes `normalizeSession` throw on every launch, even offline, and nothing catches it (there's no ErrorBoundary). A `name:{}` crashes Home while it's open. Taking over also feeds the unchecked JSON into the engine.
  - Fix: a deep `parseSession` / `parseEndedSession` guard that checks each element's type, keeps names as strings of at most 40 characters, and caps array lengths. Use it in `toActiveSession`, `toEndedSession` and the storage guards.
  - Fix: require `ended.id === row.id` in `toEndedSession`. Shared Ended sessions are deduplicated by the id inside the JSON (store.ts:442-448), so today one entry can replace or hide another.
  - Fix: add a root ErrorBoundary with a "Clear shared data" action that removes the `bq:v1:shared-*` keys.
- ✅ **S2. The host can create Ended sessions at will** (firestore.rules:373-393). The Active session doesn't have to end; any number can be created with any id, a host who was removed can still create them, and `endedAt` can be any number. Fifty Ended sessions with `endedAt=9e15` would permanently hide the Club's real history.
  - Fix, host branch: `!existsAfter(<activeSession/current>)`. Store an unchangeable `sessionId` on the Active session record and require that the Ended session's id equals it.
  - Fix, both branches: `endedAt is int && endedAt >= 0 && endedAt <= request.time.toMillis() + 300000`.
- ✅ **S3. The Make shared club import window can be held open forever** (firestore.rules:108-113). Club create doesn't check `createdAt`, so the creator can set it to a date in 2100, and the 1-hour import window (:391) never closes.
  - Fix: on create, require `keys().hasAll([...])` and `createdAt == request.time`. The client already writes `serverTimestamp()`.
- ✅ **S4. A deleted Club's id can be re-created to read its leftover history** (firebaseClubs.ts:534-577, firestore.rules:108, :400-402). When an Organizer deletes a Club that has other members, its Ended sessions stay behind. Anyone who knows the id can then create `clubs/{id}` again and read them. Separately, any Organizer can already wipe history by shrinking `memberUids` to just themselves, deleting it, and restoring the list. The rule comment at :362-363 and :397-399 is false.
  - Fix: allow any Organizer to delete Ended sessions, and make `deleteWholeClub` always delete Ended sessions and requests before the Club record. Optionally keep a tombstone Club record. Correct the comments.

### Offline and sync

- ✅ **O1. A request can be marked `applied` before any uploaded copy contains it** (hostRequests.ts:9-18, :81, :135; index.ts:191-196). Confirmed by probe. `versionOf` numbers a copy only when it's first seen, so a plain host change that is still uploading gets its number after a request was applied on top of it. The request is then marked applied while the server holds a copy without it. If someone takes over, or the phone dies, the request is lost, but the Player still sees "applied".
  - Fix (preferred): store `appliedRequestIds` in the Session. A request is marked applied when an uploaded copy contains its id, and ids already in the copy are skipped. This also fixes the false "skipped" after a reload (later item L-O6).
  - Minimum: number every copy the first time it's seen.
- ✅ **O2. When storage is nearly full, the Active session can silently fail to save, breaking ADR-0005** (storage.ts:111-117, :200-202, :219-221, :272-286; store.ts:440-464). Confirmed by probe. The cache of Shared Ended sessions fills localStorage up to the limit. After that, the device Session or a hosted Session is not saved, and it's gone after a reload.
  - Fix: save Active sessions with `writeOrThrow`. If the quota is exceeded, free space in this order and retry: (1) the Shared Ended sessions cache (the server has those), (2) copies of other Clubs' Sessions this device only watches, (3) the oldest device Ended sessions.
  - Fix: cap the Shared Ended cache by size (about 1.5 MB in total), not "whatever fits", and stop storing hosted Ended sessions in both caches.
- ✅ **O3. Ending a Session on bad signal can bring it back on the next launch, and the Club never gets the Ended session** (firebaseSessions.ts:426-463; store.ts:212). `endSharedSession` waits for `getDoc` and `getDocs(requests)` from the server before `batch.commit()`. On a dead network that still reports as online, those calls can stall indefinitely. Meanwhile `endedHere` lives only in memory. The result: the Session comes back on the next launch, other Organizers see it frozen, and starting a new Session fails with `session-exists`.
  - Fix: read from the cache only (`getDocFromCache` / `getDocsFromCache`; the host's requests listener keeps that cache warm) and commit before waiting on the network. Persist `endedHere`, and drop ids once the server reports the Session gone.
- ✅ **O4. Make shared club loses Session changes made during the conversion, and shows the Session twice** (clubs.ts:136-165; firebaseSessions.ts:353-379; store.ts:353-357, :385-399). The Session is captured before the upload, and when the upload succeeds, that early copy replaces the device Session, dropping any Matches played while "Sharing…" was in progress. The resume branch marks a fresh copy as already uploaded. While the conversion runs, the observer also adds the Club's Session, so Home shows two Resume cards.
  - Fix: after the server confirms, re-read `getSession()`. If it's the same Session, call `setHostedSession(clubId, sessionForSharing(latest, …))` without marking it published, and do the same in the resume branch.
  - Fix: in `getActiveSessions`, hide a shared entry whose `session.id` matches the device Session or whose Club is still Local.

## Production setup checklist (not code: do before pointing at a real project)

1. Create the project and turn on Anonymous Auth. Create Firestore in production mode, not test mode, which leaves it wide open for a limited time.
2. Deploy `firestore.rules` and add a production alias to `.firebaserc`.
3. Turn on App Check (reCAPTCHA Enterprise or v3) at `initializeApp` and enforce it for Firestore and Auth. Until then, scripts can create Accounts, Clubs and large documents without limit.
4. Restrict the API key to the site's HTTP referrers and to the Identity Toolkit, Token Service and Firestore APIs.
5. Stay on the Spark plan or set a budget alert. On Spark, running out of quota takes the app down for the day.
6. Check that the lazy-loaded Firebase chunk is precached for offline cold starts. Workbox skips files over 2 MiB by default.

## Later (each worth a ticket)

### Security
- L-S6. Size limits are far above real data: `sessionJson` is capped at 700 KB and `endedJson` at 400 KB (rules:248, :380). Measure real sizes and cap at about twice that.
- L-S7. A member can make unlimited requests (rules:321-335). App Check helps; so would deterministic ids like `uid + '-NN'` (at most 100 per member per Session).
- L-S8. `memberUids` and `organizerUids` have no size or type limit (rules:117-125). An Organizer can also add any uid without a row, which pushes an unwanted Club onto that person's Home. Cap both at 200 and consider a consent step.
- L-S9. `hostName` can be anyone's name (rules:262, :286). Require `hostName == get(/accounts/$(request.auth.uid)).data.name`.
- L-S10. The Account ID format isn't checked (rules:58-64, 75-83). Add `matches('^[a-z0-9]{1,12}-[a-hjkmnp-z2-9]{4}$')`.
- L-S11. Privacy:
  - Account IDs can be guessed to find a uid and name.
  - Members can see each other's uids.
  - Delete Account leaves the person's name in Session snapshots, roster rows, `hostName`, and the permanent `accountIds` → uid record, and doesn't clear Firestore's IndexedDB cache. Use `terminate()` + `clearIndexedDbPersistence()`, and say all of this in the Delete Account copy.
- L-S14. Security headers: a CSP whose `connect-src` allows only Firebase, plus `frame-ancestors 'none'` and `X-Content-Type-Options`.

### Offline and sync
- L-O5. A stale report can demote a host who has just taken over or started (firebaseSessions.ts:110-118, sharedSessions.ts:36-38). Ignore reports that name another host with an `updatedAt` at or before the takeover.
- L-O6. After a reload, requests that were already applied come back as "skipped" on the Player's side. Fixed by O1's `appliedRequestIds`.
- L-O7. Upload refusals are misread. A network failure in the follow-up read is treated as `not-found` (firebaseSessions.ts:413-422), and `forbidden` while still the host (index.ts:131-138) silently stops the uploader.
- L-O8. A stale hosted Session can stay on a device that was offline while someone took over and ended it (sharedSessions.ts:40-43). Drop it when the server confirms there's no Session.
- L-O9. With two tabs, a background tab rewrites the hosted copy with stale data, and its refused request marks clear the applied list (store.ts:126-138, :227-230; hostRequests.ts:118-124). Give hosted copies their own key, written only by engine operations.
- L-O10. An offline cold start wipes the Shared clubs, because the Shared clubs listener lacks the guard the Session observers have (firebaseClubs.ts:341-378).
- L-O11. Delete Account can stall halfway when the connection drops (firebaseBackend.ts:213-235). Clear shared data once the server confirms the Account deletion, sign out before `createAccount` if an Account existed before, and use `confirmed()` rather than `settle`.
- L-O12. Clock skew after a takeover. For shared Sessions use `now = max(Date.now(), lastChangeAt(session))`.
